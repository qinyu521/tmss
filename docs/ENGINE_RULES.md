# 规则引擎说明

所有规则实现于 `packages/shared/src/engine`，数值在 `packages/shared/src/balance.ts`。前端不参与结算。

## 1. 回合计序

一回合 = 7 天。`runTurn` 顺序：

1. 记录回合始事件，并按存档种子计算本旬**签筹**（确定性批次 + 君主统率/谋略修正），确定三势力行动顺序；同一存档重放结果一致，玩家不保证先手。
2. 公开外交命令（`diplomatic_action`）在旬初先行校验结算，使 NPC 能对同回合的宣战/结盟作出反应。
3. 玩家其余 `pendingOrders` 与 `generateNpcOrders` 基于**同一份局面**生成，再按签筹交错逐条重新校验（权限/资源/道路/上限）；合法即应用，非法生成 `order_rejected` 并说明原因。NPC 命令同样必须通过 `validateOrderForFaction`，不能绕过玩家命令使用的规则。
4. 行军与战斗：多军行军按种子顺序处理（避免玩家部队固定先动），按回合天数推进路线，跨州府、遇敌结算。`army.stance` 参与战力修正：进攻方行军突击 +6%，守方结阵驻防 +8%，行军方遭袭 -5%，溃退方 -15%。
5. 经济账本：产出、税赋、军饷、消耗、短缺惩罚、兵员恢复、州府库存与治安漂移。
6. 政治机制：部落忠诚/协调度、皇子影响力/朝局稳定、世家支持/中央权威。
7. **人物生命周期：衰老死亡掷骰、权力继承、玩家身份转移、高潜力成长（见 §6.6）。**
8. 威胁更新与边境情报。
9. 重建势力状态标签。
10. **终局判定：任一势力据有全部州郡即天下一统；玩家失尽州郡与野战军即社稷倾覆。结果写入 `state.outcome`，API 随后拒绝新命令与推进回合（409 `GAME_OVER`）。**
11. 生成史官条目（事实层 + 文学层 + 推断层）。
12. 日期 +7 天，清空命令队列。事件入库，状态入快照。

## 2. 命令与权限

唯一权限矩阵：`ROLE_ALLOWED_ORDERS`（shared/constants.ts）。

| 命令 | 君主 | 州牧 | 将军 | 军师 |
| --- | --- | --- | --- | --- |
| move_army | ✓（全军） | 仅驻本州部队 | 仅自己统率部队 | ✗ |
| rest_army | ✓ | 仅本州 | 仅自己 | ✗ |
| scout | ✓ | ✓ | ✓ | ✓ |
| recruit / levy / trade | ✓ | ✓ | ✗ | ✗ |
| appease_tribe（匈奴） | ✓ | ✓ | ✗ | ✗ |
| balance_princes（大雍，仅君主） | ✓ | ✗ | ✗ | ✗ |
| negotiate_house（大楚） | ✓ | ✓ | ✗ | ✗ |
| appoint（君主） | ✓ | ✗ | ✗ | ✗ |

每回合最多 6 条命令；同类型上限：侦察 2、征粮/加税 3、行军/州兵 3、计谋 2、整军 2、其他 1。

### 2.1 分兵与州兵

- `move_army` 可带 `amount`（总兵力）、`units`（特殊兵种与数量）、`commanderId`。当 `amount < 军团兵力` 或指定特殊兵种时，自动组建分遣队：特殊兵种按指定数扣减，余额由征集兵补足；分遣队必须另选统兵官，且统兵官不能同时在两支军队任职（含本回合待结算命令）。
- `dispatch_garrison` 从本国州府调出州兵（1000 至该州州兵数），生成 `isMilitia` 野战军；州府 `garrison` 立即减少，城防战守军随之下降。
- `recruit` 可选择州府、是否新建军团与统兵官；不新建时优先补入该州野战军团，否则补入州兵。

### 2.2 计谋

| 计谋 | 成本 | 目标 | 成功效果（成功率约 15%–90%） |
| --- | --- | --- | --- |
| 火攻 | 8000 两 | 敌军/敌州 | 敌军减员 5–13%、补给 -18、士气 -8；敌州州兵/粮仓受损。森林 +14%，河网 -10% |
| 断粮 | 6000 两 | 已知敌军 | 补给 -30、士气 -12、减员 2% |
| 离间 | 7000 两 | 敌军/敌州 | 敌国部落忠诚 -8 / 朝局稳定 -5 / 世家支持 -6；目标军士气 -6 |
| 伏兵 | 4000 两 | 本国州府 | 本州下一战守方 +18% 战力；山地/森林更易成功 |
| 声东击西 | 5000 两 | 敌州 | 本回合进攻该州 +12% 战力，敌州州兵 -5% |

成功率 = 基础值 + 施计者谋略/320 − 敌将权谋/420 + 地形修正；判定使用 `hash(gameId, turn, orderId, scheme)`，记录在事件 payload，可重放。计谋失败仍消耗银钱，并生成「被识破」事件。

## 3. 资源与军需

- 所有“每千人每周”系数统一经 `perThousandDemand` 换算；粮食 120 石/千人/周，等价于 0.12 石/人/周。粮账、短缺标签和 NPC 征粮阈值共用 `grainDemandForTroops`，不能直接用“兵数 × 120”。
- 人口恢复兵员系数统一使用 `BALANCE.economy.manpowerRegenPerPopulation`；季节倍率另行相乘，避免把未使用的旧系数误当成实际恢复率。
- 粮耗：`兵力 × 0.12 /回合`。匈奴远征惩罚：按距本国州府跳数增加粮耗，最多 +45%。
- 盐耗：`兵力 × 0.0015`；铁耗：`兵力 × 0.0008 + 行军军团 × 90`；马耗：`骑兵数 × 0.0024 (+匈奴 40)`。
- 税入：州府税基 × 治安/民心系数 × 势力配合系数（匈奴协调度、大雍行政/朝局、大楚世家税赋配合）。
- 军饷：`兵力 × 0.06 + 州兵 × 0.004`。
- 短缺阈值（3 回合粮/盐/铁、2 回合军饷、战马存量 <2% 兵力）→ 状态标签；库存归零时触发惩罚：
  - 粮：全军士气 -9、逃兵 1.8%、补给 -8、州府治安 -4/民心 -3、稳定 -4；匈奴更脆弱。
  - 盐：士气 -5、补给 -4、行政效率 -0.6。
  - 铁：训练 -0.8。
  - 马：骑兵编制 -2%、标签「骑兵受损」。
- 兵员每回合恢复 `控制人口 × 0.0007`，上限名义兵力 60%。

## 4. 行军

- **节点图结构**：战略地图共 72 个节点，含 24 座州府/主城与 48 个附属据点。主城之间使用 31 条原始道路连接；附属节点按种子中的父子关系接入所在州府，形成可寻路的支路。
- **独立控制状态**：每个节点有控制方、驻军、城防、补给等级与地形；附属节点的易手不自动改变所属州府行政归属。主城节点与州府的控制和驻军账本保持同步。
- **可通行规则**：己方节点可自由经过；交战势力节点可进攻，进入敌控节点时立即触发相应的节点战或州府战；未交战势力的控制节点拒止行军。
- **寻路**：在 72 节点图上使用 Dijkstra，按道路和父子支路的成本求最短路线；行军命令可通过 `targetMapNodeId` 指定具体关隘、粮仓、港埠、驻军营地等目标，未指定时默认目标州府主城。
- **行军日**：`边成本 ÷ 部队速度`；速度由兵种机动、征集兵比例与疲劳决定，范围 0.55–1.45。
- **跨回合路段进度**：州府旧路径的 `hopCosts[0]` 保存当前路段剩余日数、`currentHopDaysTotal` 保存完整时长；节点路径分别使用 `mapHopCosts[0]` 与 `mapCurrentHopDaysTotal`。未走完时按实际行军日数扣补给、加疲劳，下一回合只支付剩余日数。
- **地图军团标记**：按当前路段局部进度 `1 - 剩余路段日数 / 当前路段完整时长` 插值显示；路线线段、标记位置与节点控制层使用相同的地图节点 ID。
- **逐回合推进**：通过己方节点补给 +4；节点路线经过敌控节点时先战斗，胜利只改变附属节点控制权，攻下主城才转移整州；部分行军即时结算补给与疲劳，回合末额外行军负担按原规则结算。
- **存档 schema v4**：v1 → v2 补人物运行时数据，v2 → v3 恢复跨回合州府行军进度，v3 → v4 初始化 72 节点状态与军团节点路线。旧存档迁移幂等且不得覆盖已有节点控制方。

## 4.5 朝议与政治议案

- `court_debate` 每回合最多一项，支持军务与战备、赋役与民生、派系与朝局三类议题；每类议题仅接受对应的两种裁决方向。
- 五名在世列席官员由本国人物能力画像确定立场；先按主题能力确定列席，再按主题能力、忠诚倾向和决议方向投票。算法不使用随机数，相同世界状态与同一议案必得相同结果。
- 君主拥有额外裁决票；州牧/郡守在赋役、将军在军务、军师在派系议题上拥有专业影响。赞成票超过反对票则通过；平票仅由君主的裁决权决定。
- 提交时先检查所需资金与粮秣。只有通过的议案才扣除成本、影响军团状态、州府秩序/民心或匈奴部落、大雍皇子、大楚世家指标；未通过只留下投票记录，不产生政策效果。
- 每项朝议生成一条 `politics` 事件，记录议题、裁决、投票名单、赞成/反对票、前后状态和效果摘要；史官可以叙述该事件，但不得篡改结算事实。

## 5. 战斗

- 兵力质量：特殊兵种按攻击/防御/远程加权 × 地形修正；征集兵低权重。
- 系数：士气、训练、补给、疲劳、统兵官（统率 72% + 谋略 28%，权重显著，名将与庸将差距大）、匈奴协调度、盐/铁短缺。
- 战场变量：骑兵迂回（攻守机动差 ≥25 且平原/丘陵，攻方 +12%）、伏兵（守方 +18%）、声东击西（攻方 +12%，仅指定势力）、兵种克制（最多 +16%）。
- 守方：驻防军团 + 州兵（质量 0.45）× 城防系数（1 + 城防/120）。州兵被调出后本州守备下降。
- 随机：mulberry32，种子 = hash(seed, 攻方、州府、回合)；波动 ±12%，写入战报 `payload.seed` 可重放。
- 损失率：胜方 6%×(1.2−强度×0.7)，败方 18%×(1+强度×0.9)，上限 42%/20%。
- 战报事件携带：双方统兵官姓名/统率/谋略、战力、兵力比、随机种子、迂回/伏兵/佯攻加成、双方损失，可在史官页查看与重放。
- 战败方撤退到相邻本国州府；无路则溃散。攻方胜则州府易帜、主官由统兵官接任、治安/民心下降、州兵清零。

### 5.1 精锐编制与兵力守恒

- 初始特殊兵种不是按军团总兵力的千分之几拆成数百人小队；每个兵种通过派生档案的 `initialFormationSize` 明确初始成建制人数。
- 常规精锐初始编制通常为 8,000–10,000 人；禁卫、突击、水寨或受马匹/补员约束的专门兵种可采用 3,000–5,000 人的较小规模，并在兵种说明中体现稀有性。
- `capPerFaction` 是该兵种全势力可同时部署的总上限，不是单支部队编制；其数值须覆盖初始各军团配额并留下有限补员空间。
- 初始精锐从 `national_force_allocations` 已有兵力中扣出，剩余部分计为普通征集兵。三国初始总兵力必须仍为匈奴 400,000、大雍 800,000、大楚 300,000；不允许通过配置精锐凭空增加兵员。
- 回归测试校验每支初始精锐编制、各兵种势力总上限、军团兵力等式与三国总兵力守恒。

### 5.2 战报回放

- 回放**不是重新结算**：`buildBattleReplay(event)` 只读取 battle 事件已持久化的 `payload`（种子、兵力比、地形、城防、双方统兵官与计谋加成）与 `before/after`（双方兵力、伤亡、胜负），把真实结算结果**确定性展开**为 3-6 个阶段。 前端再把阶段播放为 Three.js 战场视图，按兵力比例显示双方阵列、地形、接战/迂回/相持/决胜和溃退；不再通过动画计算伤亡或改变胜负。WebGL 不可用时回退为二维阵列演出。
- 阶段编排：佯攻（如有 `diversionBonus`）→ 接战 → 伏兵（如有 `ambushBonus`）→ 骑兵迂回（如有 `maneuverBonus`）→ 相持 → 决胜。
- 伤亡按阶段权重分摊并累计取整，各阶段兵力单调递减；**最终阶段兵力精确等于事件 `after.attackerRemaining / defenderRemaining`**，伤亡总数与胜负不得与事件矛盾。
- 随机只来自 `mulberry32(payload.seed)`；同一事件多次构建结果完全相同，可用于校验与前端分镜播放。
- 接口：`GET /api/games/:id/battles/:eventId/replay`。战报属交战公开内容，直接返回完整回放。

## 6. 三国机制

- **匈奴**：协调度 = 58 + (平均部落忠诚 − 55) × 0.7（0-100）。可统一调动系数 = 0.45 + 协调度/200（0.45-0.95），直接折减野战兵力与战力；部落忠诚 <38 时拒命，驻地军团不可行军；每两回合产生战利品/继承类政治事件。
- **大雍**：皇子影响力按野心、信任、朝局漂移；最高影响力超过 62 会持续压低朝局稳定；稳定 <34 触发夺嫡危机：行政效率降至约 52-60，征募成本 +30%。
- **大楚**：世家支持每回合 -0.35，税赋配合 = 0.6 + 支持/250；平均支持 <38 触发集体抵制：征兵被拒、税收效率下降。协商可 +8 支持（耗银 12000，2 回合冷却）。

## 6.5 季节系统

季节由 `GameDate.month` 纯函数推导（`engine/season.ts` 的 `seasonOf`）：3-5 月春、6-8 月夏、9-11 月秋、12-2 月冬。全部系数集中在 `balance.ts` 的 `seasons` 块，均为温和修正项，不颠覆基础玩法。

| 修正 | 春 | 夏 | 秋 | 冬 |
| --- | --- | --- | --- | --- |
| 州府粮产 | ×0.9（青黄不接） | — | ×1.6（秋收） | ×0.35（冬藏） |
| 盐产 | — | ×1.2（晒盐） | — | — |
| 兵员恢复 | ×1.2 | — | ×1.3 | — |
| 匈奴军队粮耗 | — | — | — | ×1.25（草料难继） |
| 河网州府税收 | — | — | — | ×0.9（封冻） |
| 行军疲劳（每跳） | — | ×1.2；匈奴再 ×1.15（不耐暑） | — | — |
| 河网边行军成本 | — | — | — | 匈奴骑兵为主部队 ×0.8（封冻涉渡） |
| 河网地形战斗 | — | — | — | 水军袭扰 ×0.8；弓骑/轻骑 ×1.1 |

- 经济修正在 `computeEconomy` / `runEconomy` 中按当前月份应用。
- 行军成本修正在 `dayCostsFor`（接受 `routeTypes` 与 `season` 参数，保持纯函数与确定性）；疲劳修正在 `processMovement`（出处：`BALANCE.army.fatigueMarchPerDay` 乘以 `marchFatigueSeasonFactor`）。
- 「河网/水路」边按 `route_type` 中文关键词判定（河/江/漕/渡/航）；「骑兵为主」指全军骑马兵力占比 ≥ 50%。
- 战斗修正在 `armyPower` 的地形修正处叠加，只作用于 `river` 地形州的冬季战斗。
- 事件：`turn_start` 摘要附当回合季节与一句影响；月份进入 3/6/9/12 的第一回合额外发一条 `season` 类型事件（司天监发布）。玩家视图 `PlayerView.season` 携带季节名与提示，顶栏展示。

## 6.6 人物生命周期（schema v2 起）

每回合在政治机制之后结算一次（`engine/lifecycle.ts` 的 `runLifecycle`）。`GameState.characters` 记录每个人物的运行时状态：`alive / ageBand / deathTurn / deathCause / growthNote / attrs`（成长覆盖值）；种子 JSON 永不改写，缺失条目按在世处理（`isCharacterAlive`）。

### 死亡概率（每回合，数值在 `balance.ts` 的 `lifecycle` 块）

| 年龄段（种子 age_band 词表） | 每回合基础概率 |
| --- | --- |
| 青年 | 0.1% |
| 壮年 | 0.2% |
| 中年 | 0.5% |
| 老成（词表最高龄档，按老年档处理） | 1.5% |
| 词表外（缺省） | 0.2% |

- 本回合参战的部队主将（`army.lastBattleTurn === 当回合`，战斗结算时写入）额外 +1.5% 战死概率。
- 随机：`mulberry32(hashString("{seed}-life-{turn}"))`，遍历 336 人各掷一次，可重放、同种子完全一致；不使用 `Math.random()`。
- 死因：参战者为「战死」；老成为「寿终」；中年为「病逝」；青年/壮年为「暴卒」。
- 每次死亡生成唯一 `succession` 事件（前后状态、死因、继任者与随机种子证据俱全），同势力玩家可见。

### 继承规则（死亡当回合立即结算，保证权责空位由活人接任）

| 死者身份 | 继任者 | 附带影响 |
| --- | --- | --- |
| 州府主官 | 种子该地区副手（deputy_id，需在世且同势力）优先；否则同势力在世、未主政他州者中治理最高者 | 更新 `region.governorId/Name` |
| 部队主将 | 种子该军区副将优先；否则同势力在世、未统军者中统率最高者 | 士气 -8 |
| 匈奴部落首领 | 种子该部继承人（heir_id）；已故则同势力治理最高者 | 部落忠诚 -12 |
| 大楚世家家主 | 种子继承人（heir_id）；已故则同势力治理最高者 | 支持度 -6 |
| 大雍皇子 | 退出派系序列，影响力由其余皇子均摊；储君亡故则由影响力最高者继为储君 | 朝局稳定 -10 |
| 玩家人物 | 君主身份：在世储君优先，否则同势力治理最高者；其他身份：同身份类型优先、潜力最高者次之 | `playerPersonId/Name` 更新，role 不变，玩家不进入「死人视角」 |

- 命令校验同步收紧：已故人物不能被任命（`PERSON_DEAD`）、不能统兵（`COMMANDER_DEAD`）；自动选将（分兵/征兵/州兵）跳过已故者。
- 史官：君主/皇子/部落首领/世家家主/部队主将身故时，本回合 chronicle 必录一条 `kind='biography'` 讣闻（不被 6 条上限截断，每回合最多 3 条），facts 取自事件，literary 为悼词模板。
- 视图：`PlayerView.deceased` 下发本国已故名单；`/api/characters` 与 `/api/characters/:id` 携带 `gameId` 查询时合并该局 `alive/deathCause/runtime`（含成长备注与有效属性覆盖值）。

### 成长

- 每年（每 52 回合，`turn % 52 === 0`）结算一次：`potential ≥ 70` 且在世的人物，其当前最高主属性（治理/统率/谋略/权谋/经商，含既有成长覆盖值）+1，上限 95。
- 成长不生成事件（避免刷屏），只写 `growthNote` 与 `attrs` 覆盖值，在人物面板与玩家视图（统兵官数值）可见；种子属性保持不变。

## 6.7 NPC 战略与政治决策

- NPC 只对已交战势力的接壤目标评估进攻；军团战备由兵力、士气、训练、补给、疲劳与统率共同决定，候选目标还要检查行军时间和敌方军团、州兵、城防。
- 若我军战备力量低于目标守备估值的 58%，不生成该进攻意图；AI 在具备可行目标时按统兵官能力与本国危机状态调整冒险倾向，无法合理进攻时优先考虑疲劳、补给和士气的休整需求。
- 匈奴 NPC 优先处置明确拒命的部落；大雍 NPC 在夺嫡危机、朝局低稳或某皇子影响力过高时平衡派系；大楚 NPC 在集体抵制或世家支持偏低时优先协商。
- NPC 粮秣告急阈值按“每千人每回合消耗”折算，避免将每千人耗粮误乘全军人数而导致 AI 长期误判缺粮。

## 6.8 人物目标与自主行动（schema v5）

- 不让 336 名人物每回合都执行完整 AI 决策。目标系统只评估与当前世界状态直接相关的关键角色：军团统兵官、地方主官，以及匈奴部落首领、大雍高影响皇子、大楚低支持世家家主。
- 目标由确定性规则产生并写入 `CharacterRuntime`：整军恢复战备、推进边境战事、整饬地方、向王庭施压、扩张政治影响或维护家族利益。目标包含对象 ID、开始回合、原因与上次行动回合；未解决时跨回合保留。
- 军事目标会改变 NPC 的休整优先级、进攻军团选择与进攻意愿；政治目标会影响 NPC 对具体部落/皇子/世家的安抚与协商优先级。
- 地方主官仅在秩序/民心低于规则阈值时，才可花费 4,000 两使秩序 +3、民心 +2；部落、皇子与世家目标可在四回合冷却结束且诉求仍未解决时采取有限的自主施压/扩张行动。
- 每次真实自主行动记录 `npc_action` 事件，包含人物、目标、行动前后状态和规则证据；史官可叙述事件但不能决定行动成败或修改数字。
- 玩家只能查看本势力关键人物目标；敌方目标不会从人物查询 API 暴露。旧存档通过 v4 → v5 迁移补齐 `goal=idle`，不改变原有世界数值。

## 6.9 正式外交行动与盟约（schema v6）

- 邦交关系分数与正式条约分开存储：分数表示态度，`GameState.treaties` 记录盟约起止回合与状态。v5 → v6 只补空条约账本，不把旧存档自动变成盟友。
- 国君每回合最多提交一项正式外交行动；其他身份可在朝议提出建议，但不能直接宣战或缔盟。目标不能是本势力。
- 修好使团花费 12,000 两，关系 +18（上限 100）；宣战立即跨过战争阈值，并付出声望 -3、稳定 -2；议和使团花费 5,000 两，规则依据关系、领土损失与资源短缺判断接受与否。
- 缔盟使团花费 25,000 两；关系至少 25 才能提出，按邦交与共同敌人进行确定性评估。成功后形成八回合防御盟约，关系至少 45；双方同一时间最多各有一个有效盟友，避免三国状态出现互相矛盾的三角盟约。
- 被宣战方的有效盟友会按防御盟约加入防守方；进入战争状态后，NPC 军事决策会优先选择可达的侵略方边境目标，并在存在可行目标时跳过普通攻势概率判定、立即下达反击行军。若没有可行目标，不凭空生成军队或瞬移。废约会显著降低关系并损失声望/稳定；盟约期满保留历史记录并停止自动防卫。
- 所有外交行动均写入 `diplomacy` 事件，记录行动、成本、前后关系、评估分和盟约 ID；规则结算不交给 LLM。拒绝/失败的使团仍会付出明示成本并留下记录。

## 6.10 NPC 外交决策

- 非玩家势力每三回合评估一次外交；决策完全由当前关系、战争状态、领土损失、军粮/国库压力、共同敌人和有效盟约决定，不调用随机掷骰或 LLM。
- 交战且出现战争疲劳/资源压力时，NPC 可派议和使团；没有战争、存在共同敌人且邦交达标时，可尝试提出防御盟约；和平且无盟友时，低邦交势力可在有预算时派修好使团。
- 每个 NPC 势力每次评估最多追加一项外交命令，评估频率为每三回合一次；命令仍经过成本检查，国库不足时不会执行。
- NPC 与玩家相关的宣战、议和、修好或盟约结果会作为外交事件显示；其他 NPC 内政和军事命令继续受战争迷雾保护。
- NPC 议和/结盟失败仍支付使团成本并留下记录；AI 不会跳过外交规则直接修改战争或盟约状态。

## 7. 情报与信息

- 玩家视图只下发本国精确数值；外国州府只给控制者、地形、城防、威胁。
- 外国部队仅在「有斥候情报」或「位于本国邻州」时显示；兵力为估算区间（±25%）。
- 侦察产生 `IntelEntry`：来源、可靠度、发生/获知时间、证实状态与估算值；估算是估算，不是事实。
- 每回合烽燧可能产生「未证实」邻国兵团动向，不提供精确兵力。

## 8. 史官

- 输入仅为本回合已结算事件（玩家可见）。
- `facts` 直接引用事件 summary / evidence，不得改写。
- `literary` 为模板文风，明确标注「文学润色，不改变事实」。
- `inference` 为史官推断（如兵力比接近时判断难以再战），明确标注。
- 默认模板生成；任何 LLM 都不得写回状态。

### 8.1 可选 LLM Provider

- 配置全部走环境变量：`LLM_PROVIDER` / `LLM_API_KEY` / `LLM_BASE_URL` / `LLM_MODEL` / `LLM_TIMEOUT_MS`；缺省关闭，无密钥时游戏完整可玩（本地模板史官）。
- 接口为 OpenAI 兼容 Chat Completions（`POST {baseUrl}/chat/completions`），使用全局 fetch，无新增依赖。
- 触发方式为玩家显式调用 `POST /api/games/:id/chronicle/llm { turn }`，结算流程本身永不自动调用 LLM。
- 只读原则：发给 LLM 的内容仅限该回合史官条目的 `title`/`facts` 与对应事件的 `summary`；不发送任何其他数据库世界状态。
- LLM 只允许产出 `literary`（≤80 字）与可选 `inference`（≤60 字），prompt 明令禁止改动数字、伤亡、任免与领土结果；输出经严格 JSON 校验，超长截断，未知条目丢弃。
- 回写只更新表达层字段并把 `generatedBy` 标为 `'llm'`；`facts`、标题与来源事件永不回写。
- 失败回退：无配置返回 `LLM_DISABLED`（503），请求失败/超时/输出非法返回 `LLM_FAILED`/`LLM_BAD_RESPONSE`（502），原有模板条目保持不变。

## 9. 存档与回放

- 存档为完整 GameState JSON 快照（当前 schema v2）+ 事件/史官表。
- 迁移框架：`migrateState` 先做跨版本幂等修补，再按 `MIGRATIONS` 数组（`{ from, to, apply }`）依版本链顺序迁移；新增版本只需追加一项。v1→v2 补 `characters` 全员在世。
- 读档恢复状态并删除存档回合之后的事件记录，避免时间线分叉。
- 自动存档每回合生成，保留最近 10 份；手动存档最多列 30 份。
- 战斗随机种子在事件 payload 中，可用于同版本重放校验。
