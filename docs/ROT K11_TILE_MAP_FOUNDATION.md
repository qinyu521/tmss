# 三国志11 高保真重构：地格地图基础规格

> 状态：设计基线；本文件不代表地图引擎已经实现。
> 目标：把现有节点式战略地图逐步迁移为“地图地格是空间事实来源”的单机策略游戏架构，优先还原可观察的玩法行为，而非复制原作专有代码或资源。

## 1. 不可妥协的架构决策

1. **地格是空间权威数据**。城市、设施、部队、道路、火源和战场效果都必须映射到地图格；不能再以 72 个节点之间的抽象边作为实际移动与交战的唯一依据。
2. **地图模拟与渲染分离**。规则引擎只读写确定性的地图状态；Three.js 只负责显示状态与接收用户输入，不能自行决定战斗结果。
3. **移动必须逐格合法**。部队寻路产出可复现的地格路径；每个回合根据兵种、地形、道路、科技、状态和补给推进有限距离。路径不可达时拒绝命令并给出原因。
4. **同一地图承载战略与战术**。出征、行军、接敌、设施攻击、野战和围城均发生在同一张地格地图；战报可视化不能冒充真实战斗。
5. **旧存档必须迁移或明确拒绝**。地图 schema 变更必须新增版本迁移、幂等测试和回滚策略，不得静默丢失城市归属、部队或事件。
6. **规则确定性优先**。相同存档、命令顺序和随机种子必须得到相同的状态变化；AI 叙述层不能裁决游戏事实。

## 2. 目标数据模型

建议在 `packages/shared` 增加独立地图模型，不直接将新字段塞进渲染组件：

- `WorldMapDefinition`：地图宽高、投影/坐标约定、地格静态地形、海陆、河流、道路、桥梁、关隘和地形阻挡。
- `TerrainCell`：稳定的 `cellId`、整数 `x/y`、terrain、elevation、passability、roadType、riverCrossing、regionId。
- `MapObject`：城市、港口、关隘、资源点和可建造设施的静态定义及格坐标。
- `MapRuntimeState`：地格控制方、设施耐久、火势/陷阱、当前回合状态等动态信息。
- `ArmyPosition`：部队格坐标、当前路径、路径索引、剩余移动力、当前目标、补给与疲劳。
- `MovementProfile`：兵种移动成本、地形禁行规则、道路收益、水域限制和科技修正。

静态地图定义与单局动态状态分开存储。任何随机地图生成都必须使用显式种子，正式剧本地图应有版本号与校验和。

## 3. 移动与寻路规则

- 采用整数格坐标作为规则坐标；视图坐标仅在渲染层转换。
- 使用 Dijkstra/A* 计算加权最短路径；启发式必须可采纳，且同成本路径采用稳定的 tie-break 规则。
- 移动成本由地形基础成本、道路类型、兵种适性、科技、季节/天气、负重或兵力规模（如设计要求）组合计算。
- 不可通行地格、未满足条件的河流/海域和敌方控制造成的限制必须在规则层判定。
- 每回合推进移动点而非把部队直接传送到目的地。路径变化、道路中断、地格易手或部队被拦截时，重新规划或停下并生成事件。
- 接敌触发必须基于实际相邻关系、同格冲突和当前敌对状态；不允许仅凭“到达某州府”自动发生战斗。
- 战斗和移动的兵力、伤亡、补给、士气、疲劳必须使用统一单位，禁止将“每千人”与“每人”混用。

## 4. 战斗与地图状态闭环

野战、攻城、设施攻击都要由同一规则层结算。战斗输入至少包括：双方部队、将领属性/特技、兵种、兵力、士气、训练、气力、补给、地形、相邻支援、设施效果和可复现随机种子。

战斗输出必须明确改变真实状态：兵力损失、士气/训练/疲劳、将领状态、设施耐久、地格控制、撤退路径、粮草消耗和事件日志。动画只展示已经由规则引擎确定的动作；动画结束不能反向改写胜负。

## 5. UI/UX 目标

- 支持大地图拖拽、缩放、定位城市、选择地格、显示地形与势力控制图层。
- 鼠标悬停可查看地格/设施信息；点击部队后展示可达范围、移动成本与路径预览。
- 选择目的地后先显示路径和预计耗时，确认后才提交命令。
- 地图对象、路径预览、选中状态与规则状态分层；低画质模式只降低装饰与细节，不改变游戏规则。
- 不能用节点连线示意图替代连续地格地图；不能让相邻节点之间的部队跳跃作为正常移动表现。

## 6. 迁移策略

### 阶段 A：数据与渲染原型
1. 定义地格 schema、地图版本和验证器。
2. 使用独立制作/许可的数据建立可行走的测试地图；验证陆地、河流、道路、山地与阻挡。
3. 加入格坐标/世界坐标双向转换、镜头缩放、选格与调试图层。
4. 不改变旧战役规则；新地图先以 feature flag 启用。

### 阶段 B：规则寻路
1. 建立地格寻路与移动成本单元测试。
2. 将一支测试部队从起点逐回合移动到目标，核验每步合法、耗时正确、存档读档后路径可续。
3. 为无法到达、途中道路变化、敌军拦截和目标被占领增加集成测试。

### 阶段 C：统一战场
1. 将接敌判定从“抵达战略节点”迁移到地格邻接/同格规则。
2. 将设施、火势、撤退、补给和战斗输出写入地图运行时状态。
3. 移除旧节点结算的唯一裁决权；保留州府/节点只作为地图对象或行政抽象。

### 阶段 D：内政与全战役
1. 城市建筑占格、建设与产出接入同一经济账本。
2. AI 评估地格路线、目标价值、兵力、补给和时间成本。
3. 验证攻城、野战、增援、撤退、存档迁移和长战役的确定性。

## 7. 验收标准

- [ ] 地图地格具有稳定 ID，地图数据校验可发现越界、重复 ID、无效地形和悬空引用。
- [ ] 城市/设施坐标与地图格一致，渲染层不能私自偏移规则位置。
- [ ] A* / Dijkstra 路径只经过合法地格，重复运行结果一致。
- [ ] 部队每回合仅移动有限距离，移动途中补给/疲劳按规则结算。
- [ ] 接敌由真实位置与敌对关系触发；无法通行的路线不能被接受。
- [ ] 战斗结果实际更新部队、设施、控制权与事件，不依赖动画。
- [ ] 保存并重新载入后，地格、部队路径和战斗状态保持一致。
- [ ] 全量测试、类型检查和生产构建通过；手动试玩覆盖一场行军、一次野战和一次攻城。
- [ ] 所有新增资源有明确来源/许可；不复制原作可执行代码、专有美术、音乐或大段文本。

## 8. 与现有项目的边界

现有 24 州府、72 战略节点和州府图可暂时作为行政/剧本数据来源，但不得再决定实际地格移动。现有 NPC、经济、外交、人物和史官系统可分阶段接入新地图；未完成迁移前，不宣称已经实现高保真还原。

每个阶段都应单独提交、独立测试并通过 PR 合并。不要把过时的大型 PR 与新地图重构捆绑合并。
